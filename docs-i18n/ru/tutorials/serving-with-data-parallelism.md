# Обслуживание моделей с параллелизмом данных { #serving-models-with-data-parallelism }

В этом руководстве показано, как применять в GPUStack конфигурации параллелизма данных из рецептов vLLM или SGLang cookbook: выбирать GPU, задавать параметры бэкенда, проверять рабочие нагрузки и восстанавливать развёртывание.

## Предварительные требования { #prerequisites }

- GPUStack установлен и работает. Обновите сервер, участвующие воркеры и UI до версий с поддержкой этих рабочих нагрузок. Уведомления о несовпадении версий не заменяют проверку совместимости функций.
- Подготовьте **2 Linux-воркера, каждый с 4 NVIDIA GPU одной модели и 80 ГБ видеопамяти на GPU**. Обычное развёртывание vLLM использует все восемь GPU. Обычное развёртывание SGLang использует один воркер. В примере PD один воркер выделяется для Prefill, другой — для Decode.
- Выберите `Backend Version` `0.32.0` для vLLM или `0.5.22` для SGLang и образ GPUStack Runner для ваших устройств. Парный SMG обычного развёртывания SGLang также требует метаданных зависимостей образа с `sglang-router=0.3.2`. Одной установки пакета в собственный образ для этой проверки недостаточно.
- Воркеры должны иметь возможность загружать модели из Hugging Face. Для локальных моделей используйте одинаковый путь на всех участвующих воркерах.
- Воркеры должны обмениваться данными по зарегистрированным IP-адресам, а шлюз — иметь доступ к портам их API инференса. Между воркерами рекомендуется высокоскоростное соединение. Для PD также выполните [требования к сети](../user-guide/pd-disaggregation.md#networking-requirements).

Примеры vLLM и SGLang DPA/EP используют `Qwen/Qwen3-30B-A3B`, а пример обычного SGLang DP — `Qwen/Qwen3-8B`. Они иллюстрируют размещение ресурсов. Проверьте доступную длину контекста и параллелизм запросов в своей среде: они зависят от точности весов, KV-кэша, библиотек связи и возможностей устройств.

## Шаг 1: разверните модель { #step-1-deploy-the-model }

Ниже показана настройка каждого варианта в GPUStack. Перед переходом к следующему примеру остановите предыдущее развёртывание и освободите GPU.

### Развёртывание с vLLM External-LB { #deploy-with-vllm-external-lb }

1. Откройте `Deployments`, нажмите `Deploy Model`, выберите `Hugging Face` и найдите `Qwen/Qwen3-30B-A3B`.
2. Установите `Backend` в `vLLM`, а `Backend Version` — в `0.32.0`.
3. Включите `Allow Distributed Inference Across Workers`. В разделе `Scheduling` установите `Scheduling Mode` в `Specify GPU`. Через `GPU Selector` выберите по четыре GPU на каждом воркере.
4. Добавьте следующие записи в `Backend Parameters`:

    ```bash
    --distributed-executor-backend=mp
    --data-parallel-backend=mp
    --data-parallel-size=4
    --tensor-parallel-size=2
    --enable-expert-parallel
    --data-parallel-external-lb
    --max-model-len=8192
    ```

5. Нажмите `Save`.

Эта конфигурация использует `DP × TP = 4 × 2 = 8` GPU: по два полных ранга на воркер. GPUStack назначает устройства и порты, формирует аргументы запуска каждого ранга и публикует четыре API рангов после готовности всего экземпляра.

### Развёртывание с vLLM Multi-port External-LB { #deploy-with-vllm-multi-port-external-lb }

1. Сохраните модель, версию, выбор GPU и остальные параметры из примера External-LB.
2. Замените `--data-parallel-external-lb` на:

    ```bash
    --data-parallel-multi-port-external-lb
    ```

3. Нажмите `Save`.

Развёртывание по-прежнему предоставляет четыре независимых API рангов. Встроенный DPSupervisor каждого воркера управляет двумя локальными рангами. Его общий порт проверки здоровья не является общим API инференса.

Каждый ранг должен полностью помещаться на одном воркере. Значение local DP должно быть одинаковым на всех воркерах и не меньше `2`. Если `--api-server-count` и `--prefill-context-parallel-size` заданы явно, их значение должно быть `1`. Этот режим не поддерживает `--headless`, `--grpc` и `--uds`.

### Развёртывание с vLLM Hybrid-LB { #deploy-with-vllm-hybrid-lb }

1. Сохраните модель, версию и выбор GPU из примера External-LB.
2. Полностью замените список `Backend Parameters` на:

    ```bash
    --distributed-executor-backend=mp
    --data-parallel-backend=mp
    --data-parallel-size=4
    --tensor-parallel-size=2
    --enable-expert-parallel
    --data-parallel-hybrid-lb
    --max-model-len=8192
    ```

3. Нажмите `Save`.

В этом примере доступны два общих API, каждый из которых управляет двумя локальными рангами. Шлюз выбирает общий API, а vLLM — ранг за ним. Число запросов общего API не равно числу запросов отдельного ранга.

Обычные External-LB и Hybrid-LB также поддерживают TP/PP-шарды на нескольких воркерах. Если один ранг занимает несколько узлов, на каждом нужно выделить одинаковое число устройств. Некоторые воркеры при этом выполняют только вычисления и не предоставляют API. Проверяйте фактическое размещение рабочих нагрузок.

### Развёртывание с SGLang DP и SMG { #deploy-with-sglang-dp-and-smg }

1. Откройте `Deployments`, нажмите `Deploy Model`, выберите `Hugging Face` и найдите `Qwen/Qwen3-8B`.
2. Установите `Backend` в `SGLang`, а `Backend Version` — в `0.5.22`.
3. В разделе `Scheduling` установите `Scheduling Mode` в `Specify GPU`. Через `GPU Selector` выберите четыре GPU на одном воркере.
4. Добавьте следующие записи в `Backend Parameters`:

    ```bash
    --tp-size=1
    --dp-size=4
    --context-length=8192
    --policy=cache_aware
    ```

5. Нажмите `Save`.

Обычный DP запускает четыре полные копии модели на `DP × TP = 4 × 1 = 4` GPU. GPUStack создаёт Engine и компонент SMG, использующий только CPU. Шлюз подключается к SMG. Отдельное развёртывание SMG и ручное задание `--worker-urls` не нужны. В этом примере DP attention не включён, поэтому все четыре GPU должны находиться на одном воркере.

`--policy` применяется только к парному SMG и не передаётся в Engine. По умолчанию используется `cache_aware`; также поддерживаются `random`, `round_robin`, `power_of_two` и `manual`. Запросы с одинаковым префиксом могут постоянно попадать на одну цель. Неравномерность распределения сама по себе не означает ошибку маршрутизации.

### Развёртывание с SGLang DPA и EP { #deploy-with-sglang-dpa-and-ep }

1. Сохраните выбор четырёх GPU на одном воркере и версию SGLang из предыдущего примера. Измените модель на `Qwen/Qwen3-30B-A3B`.
2. Полностью замените список `Backend Parameters` на:

    ```bash
    --tp-size=4
    --dp-size=1
    --attn-dp-size=4
    --ep-size=4
    --context-length=8192
    --policy=cache_aware
    ```

3. Нажмите `Save`.

Этот пример сочетает attention DP и EP на четырёх GPU. Не применяйте формулу обычного DP `DP × TP`, получая шестнадцать GPU. `--attn-dp-size` и `--attention-data-parallel-size` — псевдонимы; для известных версий Runner требуется SGLang `0.5.22` или новее. Старые версии используют `--dp-size=4 --enable-dp-attention`. Не сочетайте оба синтаксиса, чтобы повторно задать один и тот же параллелизм.

Для обычного развёртывания SGLang эффективное число рангов маршрутизации равно произведению DP size и attention DP size. Новый синтаксис DPA требует, чтобы TP size делился на attention DP size, а оба значения DP не могут одновременно превышать `1`; см. [SGLang Activation Logic](https://docs.sglang.io/docs/advanced_features/dp_dpa_smg_guide#activation-logic). GPUStack создаёт SMG только при числе рангов маршрутизации больше `1`. Конфигурация только с EP и числом рангов маршрутизации `1` использует Engine напрямую и не допускает обычный параметр SMG `--policy`. SGLang PD использует отдельный PD router и не добавляет SMG обычного развёртывания к каждой роли.

### Передайте управление топологией GPUStack { #let-gpustack-manage-the-topology }

В этих управляемых примерах задаются параллелизм, режим и GPU для всего экземпляра. GPUStack формирует ранги, номера узлов, адреса связи и порты. Создавать отдельное развёртывание для каждого воркера или задавать `GPUSTACK_SKIP_GPU_COUNT_CHECK` не требуется.

Оставьте `--data-parallel-rank`, `--data-parallel-start-rank`, `--data-parallel-address`, `--data-parallel-rpc-port`, `--nnodes`, `--node-rank`, `--host` и `--port` под управлением GPUStack. `--data-parallel-size-local` можно задать явно, но значение должно соответствовать фактическому выделению ресурсов.

!!! warning

    Три флага LB в vLLM взаимоисключающие. Управляемые API рангов используют TCP HTTP и не поддерживают `--ssl-keyfile` или `--ssl-certfile` на стороне Engine; настройте клиентский TLS на шлюзе. `GPUSTACK_MANUAL_DP=1` предназначен только для ручного DP с обычным встроенным бэкендом vLLM, а не для PD или SGLang. Изменение требует пересоздания экземпляров. Ручной процесс описан в [руководстве MultiProcessing](running-distributed-vllm-with-multiprocessing.md#step-2-deploy-the-model-with-the-mp-backend).

## Шаг 2: проверьте рабочие нагрузки и готовность { #step-2-check-workloads-and-readiness }

1. Разверните строку развёртывания в `Deployments` и проверьте состояние экземпляра.
2. Откройте `Workloads / ranks` в информации об экземпляре. Проверьте воркер, устройства, rank/component и готовность API.
3. Дождитесь `Running`. Завершение загрузки, запуск контейнера и готовность API — отдельные этапы.
4. При сбое откройте журнал рабочей нагрузки или `View Logs` экземпляра, чтобы определить воркер и причину. Для экспорта журналов используйте `Download Logs`.

| Пример | Ожидаемое размещение |
| --- | --- |
| vLLM External-LB / Multi-port External-LB | Четыре API рангов |
| vLLM Hybrid-LB | Два общих API, каждый управляет двумя локальными рангами |
| SGLang DP | Компоненты Engine и SMG, четыре логических ранга внутри Engine |
| SGLang DPA/EP | Компоненты Engine и SMG, четыре логических ранга в этом примере |

Читайте журналы и метрики с учётом их фактического источника. Представления логического DP в SGLang фильтруют метрики общего Engine по нативной метке `dp_rank`. Метрики без этого измерения могут не содержать данных. Не умножайте метрики общего API Hybrid или суммарные метрики Engine на число рангов. Отсутствие метрик или временно нулевое число запросов само по себе не означает сбой Engine.

## Шаг 3: проверьте в Playground { #step-3-verify-in-playground }

1. Нажмите `Open in Playground` для готового развёртывания.
2. Убедитесь, что выбрана модель этого развёртывания. Введите «Объясни параллелизм данных одним предложением.» и отправьте запрос.
3. Убедитесь, что получен ответ, затем проверьте журналы и мониторинг рабочих нагрузок, чтобы проследить путь запроса.

## Использование с разделением PD { #use-with-pd-disaggregation }

PD настраивает Prefill и Decode и выделяет им ресурсы отдельно. PD router координирует запросы и передачу KV. Прямая маршрутизация от шлюза к рангам обычного развёртывания не применяется ко всему сервису PD: точкой входа PD всегда служит router.

### Проверьте транспорт и размещение { #check-the-transport-and-layout }

| Режим vLLM | Участники Router | Ограничения транспорта |
| --- | --- | --- |
| External-LB | Основной API каждого DP-ранга | CUDA NIXL, CUDA Mooncake, Ascend Mooncake; для CUDA Mooncake каждый ранг должен помещаться на одном воркере |
| Multi-port External-LB | Основные API рангов, запущенные встроенным DPSupervisor; каждый регистрируется как DP=1 | Только CUDA NIXL; одинаковый local DP ≥ 2 на всех воркерах, каждый ранг целиком на одном воркере |
| Hybrid-LB | Общие эндпоинты воркеров, предоставляющих API; каждый регистрируется со своим local DP | CUDA NIXL, CUDA Mooncake, Ascend Mooncake; статический router CUDA Mooncake требует одинаковый local DP у всех общих API |

### Разверните группу vLLM NIXL { #deploy-a-vllm-nixl-group }

1. Создайте развёртывание для `Qwen/Qwen3-30B-A3B`. Выберите `vLLM` и `Backend Version` `0.32.0`, включите `PD Disaggregation` и выберите `NIXL` в `Transport`.
2. В `Roles` установите `Parameters and environment` в `Custom` для `Prefill` и `Decode`. Введите следующий полный список в `Backend Parameters` каждой роли. Оставьте список уровня модели пустым и сохраните управляемый платформой `Router`:

    ```bash
    --distributed-executor-backend=mp
    --data-parallel-backend=mp
    --data-parallel-size=2
    --tensor-parallel-size=2
    --enable-expert-parallel
    --data-parallel-external-lb
    --max-model-len=8192
    ```

3. Установите `Resources and scheduling` каждой роли в `Custom`. Через `Specify GPU` назначьте четыре GPU первого воркера для Prefill и четыре GPU второго — для Decode.
4. Нажмите `Save`. Дождитесь готовности Prefill, Decode и Router, затем выполните проверку в Playground, как в шаге 3.

Prefill и Decode имеют по два ранга и используют в сумме восемь GPU. Список параметров роли полностью заменяет список уровня модели, а не дополняет его. Выбранный рецепт формирует KV-коннектор, адреса ролей и параметры соединения. Вручную задавать адреса участников не нужно.

В этом примере CUDA NIXL замените `--data-parallel-external-lb` обеих ролей на `--data-parallel-multi-port-external-lb`, чтобы сохранить по два независимых API рангов с каждой стороны. Другой вариант — заменить его на `--data-parallel-hybrid-lb` и добавить `--data-parallel-size-local=2` каждой роли. Тогда каждая сторона предоставляет один общий API для двух рангов. Одновременно оставляйте только один флаг LB.

Router запускается, когда с обеих сторон есть доступные участники. Состояние `Partially ready` при запуске нормально. Готовность одного ранга или роли не доказывает работоспособность всего пути PD-запроса. CUDA Mooncake использует статический состав участников, поэтому его изменение может пересоздать router и кратковременно прервать запросы. Управление ролями и передача KV описаны в [разделении PD](../user-guide/pd-disaggregation.md). Настраивайте маршрутизацию SGLang PD через `Route arguments` роли Router, а не через параметр Engine `--policy` из примера обычного SMG.

## Шаг 4: обновите и восстановите развёртывание { #step-4-update-and-recover-the-deployment }

### Примените изменение конфигурации { #apply-a-configuration-change }

Изменение параллелизма, режима LB или размещения GPU требует пересоздания всего экземпляра.

1. Сохраните новую конфигурацию.
2. Выберите `Stop` в `Operations` развёртывания.
3. Дождитесь удаления старых экземпляров. Остановка PD ждёт подтверждения от доступных воркеров, что старые рабочие нагрузки остановлены.
4. Выберите `Start`, дождитесь готовности новых экземпляров и проверьте их в Playground. Для обычного развёртывания с включённым масштабированием по расписанию используйте `Resume Schedule`, чтобы возобновить текущее расписание. Целевое количество может остаться нулевым.

| Ситуация | Поведение при восстановлении |
| --- | --- |
| Сбой Engine/ранга в обычном управляемом экземпляре | Удаляются все эндпоинты экземпляра. После подтверждения остановки старых рабочих нагрузок весь экземпляр восстанавливается согласно `Auto-Restart On Error`. Обычные экземпляры могут восстанавливаться с текущей конфигурацией на исходном наборе воркеров/GPU. |
| В обычном развёртывании SGLang отказал только SMG | Пересоздаётся только SMG, исправный Engine сохраняется. |
| Сбой экземпляра Engine в PD без изменения конфигурации | Восстанавливается весь затронутый экземпляр, сохраняются исправная противоположная роль и другие экземпляры, обновляется состав участников router. |
| Конфигурация PD изменена | Автоматическое восстановление и пересоздание участников со старой конфигурацией приостанавливается. Остановите и запустите всё развёртывание, чтобы применить сохранённую конфигурацию. |
| Воркер недоступен, состояния старых рабочих нагрузок неизвестны | Принадлежность старых рабочих нагрузок сохраняется до подтверждения остановки. Автоматический перенос на другой воркер не гарантируется. |

Сохранение изменений не перезапускает исправные процессы немедленно. Обычное восстановление после сбоя не выбирает новые GPU. Если новая конфигурация требует иного размещения ресурсов, явно пересоздайте развёртывание, не полагаясь на перепланирование при восстановлении.

### Замените недоступный воркер { #replace-an-unavailable-worker }

Недоступность воркера означает, что GPUStack сейчас не может подтвердить состояние узла или рабочих нагрузок. Она не определяет, можно ли отремонтировать узел. Если проверка узла или сети показала, что воркер нужно заменить:

1. Выберите `Stop` или `Delete` для развёртывания. GPUStack удалит старые записи экземпляров воркеров, признанных недоступными, с истёкшим heartbeat или уже удалённых, и дождётся остановки старых рабочих нагрузок на доступных воркерах.
2. Если сохраняете развёртывание, зарегистрируйте новый воркер и обновите выбор GPU в `GPU Selector`.
3. Дождитесь удаления старых экземпляров перед выбором `Start`. Если развёртывание было удалено, создайте его заново.

!!! warning

    Удаление записей экземпляров недоступного воркера не означает остановку удалённых процессов. Если исходная машина работает, но изолирована от сети, остановите или изолируйте её старые рабочие нагрузки на уровне машины или инфраструктуры до запуска новой группы. После восстановления соединения исходный воркер очистит старые рабочие нагрузки, больше не принадлежащие действующим экземплярам. Сохранение KV-кэша и незавершённых запросов при восстановлении не гарантируется.
